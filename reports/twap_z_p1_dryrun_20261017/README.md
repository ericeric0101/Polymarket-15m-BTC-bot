# TWAP-z 執行器 P1 DRY-RUN 報告（2026-10-17）

**期間：** 2026-10-16 10:41:38 到 10-17 10:57:13（台北），共 24.3 小時，涵蓋 8 個串流。

**依事前登記：** 本報告沒有讀取任何結算結果或損益，只看機制、覆蓋率和可執行性。

## 結論

**P1 閘門：未全數通過，暫不進入 P2。**

| 閘門（spec §4） | 結果 | 判定 |
|---|---|---|
| 決策延遲 p99 < 500 ms | p99 18 ms，最大 51 ms | ✅ |
| 和記錄器 shadow 的觸發一致率 ≥ 90% | 整體 68%（23/34，因果取法）；ETH/SOL/XRP 86%（19/22）；**BTC 33%（4/12）** | ❌ |
| fail-closed 全部有原因碼，沒有 fail-open | `RULE_MATCH_FAIL_CLOSED` = 0；全部 SKIP 都有原因碼 | ✅ |
| 程序穩定，沒有 crash | 沒有 crash；但 BTC 盤口連線被斷線 511 次（1013 slow consumer） | ⚠️ |

**不一致的主因有兩個，都是資料收集的問題，不是策略邏輯：**

1. **BTC 盤口連線過載。**
   - BTC 的 5m 和 15m 共用一條連線，一天被 Polymarket 以 1013 slow consumer 斷線 511 次（執行器），記錄器也有 467 次。
   - 本地盤口在斷線前就已經落後：BTC 15m 的盤口延遲 p99 是 0.72 秒，SOL/XRP 約 0.1 秒。
   - 2026-10-17 10:56 已改成每個（幣種、長度）一條連線，修正見 `b778e78`。冒煙測試 150 秒內 0 次斷線。
2. **shadow 的盤口取樣時間不精確。**
   - 記錄器每秒取樣一次，取樣時刻落在那一秒內任意位置。最後一分鐘 mid 跳動快，剛好跨過 0.10／0.90 邊界時，shadow 和即時判斷就會不一致。
   - 現行評估程式取 `ts_sec ≤ t` 的列，但那一列可能在 t 之後最多 1 秒才取樣，等於有輕微的前視偏誤。
   - 改用因果取法（只用最後更新時間 ≤ t 的樣本）後，一致率從 62% 升到 68%。

## 建議（待使用者決定）

1. **P1 延長 24 小時：** 用今天修好的版本（每串流一條連線、盤口不再丟失）重新量一致率。
2. **需要核准的兩個機制修正，不改規則：**
   - **記錄器：** 盤口改在每秒開頭固定取樣，並記錄取樣毫秒 `sample_ms`，讓 shadow 和即時判斷看到同一時刻的盤口。
   - **評估程式：** v2/v3 改用因果取法，只用最後更新時間 ≤ 決策時點的盤口。plan_v2 §1.3 本來就寫「不晚於決策時點」，現行程式其實違反了這一點。
     - 修正必須在看到任何損益之前，寫成附錄並 commit。
3. **P2 的條件不變：** 延長的 P1 必須各串流一致率 ≥ 90% 才進入。
